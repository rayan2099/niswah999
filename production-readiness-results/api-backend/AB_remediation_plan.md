# API & Backend Audit — Phase 3: Remediation Plan

> ⚠️ **This remediation plan is PROPOSED — NOT IMPLEMENTED.** It requires technical review and a separate implementation decision. Nothing in this document should be described as fixed until code changes are completed and controlled validation is rerun. No code in this repository was modified by this audit.

---

## Root-Cause Map

| Finding | Symptom | Root cause | Confidence | Related findings | Remediation phase |
|---|---|---|---|---|---|
| AB-001 | AI features return canned fallback text instead of real answers in practice | Both the server-side and client-side Gemini integrations were built against a request/response shape (`v1beta/interactions`, `input`/`system_instruction`/`steps`/`outputs`) that does not match Google's documented `generateContent` API — most consistent with an AI-agent-generated integration that hallucinated (or confused with OpenAI's Responses API) the provider's real contract, then was copy-pasted into a second file | LIKELY, HIGH — needs one live call to confirm/deny | AB-002 (both integrations share the same broken shape) | R1 |
| AB-002 | Gemini API key is extractable from every shipped app build; two AI features have zero backend mediation | `.env` was chosen as a build-time secret-loading mechanism and then declared as a Flutter **asset** (`pubspec.yaml:73`), which bundles it into the compiled package rather than keeping it server-side only; `AiAdvisorService`/Dream Interpreter were built to call the provider directly instead of going through a proxy, unlike the (correctly designed) `dr-niswah-chat` function | CONFIRMED | AB-001, AB-012 | R1 |
| AB-003 | A network retry after a chat send can duplicate `chat_messages` rows | No idempotency key/request ID was designed into the two-insert (user message → assistant message) flow | CONFIRMED | — | R2 |
| AB-004 | A slow Gemini response can hold the server-side function open indefinitely (bounded only by platform default) | The server-side `fetch()` was written without an `AbortController`, while the client-side equivalent was; inconsistent resilience patterns between the two copies of essentially the same call | CONFIRMED | AB-001 | R2 |
| AB-005 | Wildcard CORS on an authenticated endpoint | Default/example Supabase Edge Function CORS boilerplate (`Access-Control-Allow-Origin: '*'`) was carried into production code without scoping to the app's actual origins | CONFIRMED | — | R3 |
| AB-006 | No size/shape bound on chat request fields | Validation was written to the minimum needed to avoid a null-pointer/empty-string bug, not to bound cost/storage/abuse | CONFIRMED | AB-008 | R2 |
| AB-007 | Internal exception text can reach the client | The generic top-level `catch` was written for developer convenience (see the real error immediately) rather than a production-safe sanitized envelope | CONFIRMED | — | R2 |
| AB-008 | No cap on chat request volume per user | Rate limiting was never designed in; Supabase does not provide it by default | CONFIRMED (absence) | AB-002, AB-006 | R3 |
| AB-009 | The only deployed endpoint (`index.ts`) has no test coverage of its own | Testing effort went into the pure, easily-unit-testable helper (`pregnancy_status.ts`) and stopped there; the handler itself (auth, validation, side effects, Gemini call) was never wrapped in an integration-test harness | CONFIRMED | AB-001 (a test harness would likely have caught this) | R3 |
| AB-010 | Four different error-handling strategies across four repositories, none of them the shared `Failure` type | Each feature's data layer appears to have been implemented independently (possibly by separate AI-agent sessions/prompts) without a shared repository base class or error-mapping convention being enforced | CONFIRMED | — | R2 |
| AB-011 | No explicit timeout on any Supabase table call | Never configured; relying on package defaults that were never audited | CONFIRMED (absence); package defaults UNKNOWN | AB-004 | R3 |
| AB-012 | Fiqh source-trust rule is bypassable in a modified client | Same root cause as AB-002 — no backend mediation for this feature | CONFIRMED | AB-002 | R1 (bundled with AB-002 fix) |
| AB-013 | No server-enforced max page size | Same as AB-006 — validation written to functional minimum, not abuse-resistance | CONFIRMED | AB-006 | R3 |

## Remediation Principles Applied

| Principle | Application here |
|---|---|
| Server is authoritative | AB-002/AB-012 fix moves Gemini calls for AI Advisor and Dream Interpreter behind a Supabase Edge Function, matching the `dr-niswah-chat` pattern, so no client-embedded provider key exists |
| Explicit contracts | AB-001 fix requires re-deriving the Gemini request/response schema from Google's actual current API documentation (live verification step, not assumption) |
| Fail accurately | AB-007 fix replaces raw `error.message` passthrough with a small fixed set of sanitized client-facing messages, logging the real detail server-side only |
| Idempotent retries | AB-003 fix adds a client-generated `requestId` (e.g. UUID per send attempt) persisted alongside the message, with a unique constraint / upsert-on-conflict to make retries safe |
| Bounded external calls | AB-004/AB-011 fix adds explicit timeouts to every external network call, server- and client-side, with a consistent policy |
| Auth at resource boundary | Already largely correct (AUTHN-01/AUTHZ-01/02 passed) — no change needed there, preserved as-is |
| One error envelope | AB-010 fix introduces a shared repository error-mapping helper that all four (and future) repositories funnel `PostgrestException`/`AuthException`/network errors through into the existing `Failure` hierarchy in `lib/core/errors/failures.dart`, instead of ad hoc swallow/throw-bespoke-type per file |
| Compatibility before cleanup | R1 items (AB-001, AB-002) are scoped as additive (new Edge Function, corrected request shape) rather than a rewrite of chat/thread schemas, to avoid breaking existing `chat_messages`/`chat_threads` data |
| Test the contract | R3 explicitly adds integration-style tests for `dr-niswah-chat`'s `Deno.serve` handler (auth rejection, validation rejection, red-flag path, Gemini-failure fallback path), not just the pure helper |

## Backward-Compatibility Requirements

- [x] Existing client versions identified: current shipped client calls `dr-niswah-chat` with `{threadId, content}` and expects `{reply, urgent, messageId}` — R1/R2 changes preserve this envelope exactly; only internal implementation and (for R2-d) the exact text of `error` messages change.
- [x] Compatibility window defined: R1-c's new proxy functions are additive; the existing direct-to-Gemini client code path should be kept behind a flag until the new functions are confirmed working in production, then removed in a follow-up release — not this same release.
- [x] Old field/route behavior documented: N/A — no fields are being removed or renamed in this plan.
- [x] Deprecation plan exists: direct Gemini client key (`GEMINI_API_KEY` in `.env`) should be removed from the asset bundle only **after** R1-c ships and is confirmed working, not in the same build.
- [x] Migration sequencing defined: R1-a → R1-b → R1-c, then R2 items (can proceed in parallel with R1 once R1-a's findings are known), then R3 items.
- [x] Client rollout sequencing defined: server-side changes (R1-a/b, R2-a/b/c/d, R3-a/b/c/d/e) can ship without a client update; R1-c and R2-a require a client update to actually take effect (new invoke calls, new `requestId` field) — plan a coordinated release.
- [x] Rollback documented: per-row above; all changes are additive or simple code reverts, no destructive migration is proposed.
- [x] Monitoring exists for old/new usage: not currently — recommend adding basic Edge Function invocation/error-rate logging (Supabase function logs already capture this; no additional dashboard exists in-repo) as part of R1-c rollout so the direct-vs-proxied Gemini traffic split can be observed during the deprecation window.
