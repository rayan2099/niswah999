## Phase 4 — State Machine Validation

Production `FiqhCycleState` enum: `insufficientHistory`, `tahara`, `haid`, `needsAdvisory`. Compared against the charter's suggested full set (`UNKNOWN`, `BLEEDING_UNCLASSIFIED`, `HAYD`, `ISTIHADA`, `TUHR`, `NIFAS`, `PREGNANCY_RELATED_STATE`, `REQUIRES_MORE_INFORMATION`, `REQUIRES_SCHOLAR_REVIEW`):

| Charter state | Production equivalent | Notes |
|---|---|---|
| `TUHR` | `tahara` | Direct match |
| `HAYD` | `haid` | Direct match |
| `REQUIRES_MORE_INFORMATION` / `REQUIRES_SCHOLAR_REVIEW` | `needsAdvisory` (single combined state) | The evaluator does not distinguish "we don't have enough facts yet" from "the facts are clear but exceed the boundary and a scholar should weigh in" — both collapse to the same `needsAdvisory` state. Fails safe (never asserts a wrong `haid`), but loses explanatory precision. |
| `UNKNOWN` | `insufficientHistory` | Direct match, mapped to `tahara` for *display* purposes in `CycleStatusEngine` (a deliberate, commented design choice — "if the fiqh evaluator falls back to insufficientHistory... daysIntoCurrentEpisode must not leak through, or state and daysIntoCurrentEpisode would disagree") |
| `ISTIHADA` | **No distinct state** | Bleeding beyond the madhhab's maximum duration produces `needsAdvisory`, not a distinct `ISTIHADA` classification. See FIQH-6. |
| `NIFAS` | Handled entirely outside this state machine, via `PregnancyStatusEngine`/`FiqhReportInsights.nifas` | A deliberate, structurally separate path (nifas priority is checked *before* falling into cycle-state logic in `FiqhReportInsightsEngine.analyze`) — not obviously wrong, but means "the fiqh state machine" is really two separate machines that happen to be composed in report generation, and only one of the two (`FiqhCycleState`) exists in the dashboard/AI-context discussion at all. |
| `PREGNANCY_RELATED_STATE` | Modeled separately via `pregnancy_profile`/`PregnancyStatusEngine`, not fused into `FiqhCycleState` | Same observation as `NIFAS`. |

**Transition triggers verified**: `hasSufficientHistory` (history dependency) → `insufficientHistory`; `isBleeding=false` → `tahara`; Hanafi-only purity-before check (history + duration dependency) → `needsAdvisory`; duration outside `[minimum, maximum]` → `needsAdvisory`; otherwise → `haid`. No transition depends on AI interpretation anywhere in this evaluator — confirmed by direct read, the function takes only deterministic inputs (`madhhab`, booleans, `Duration`s) and returns a pure result. This is a genuine, verified PASS against the charter's "No state transition may depend solely on AI interpretation" rule.

## Phase 8 — Madhhab Switching

`MadhhabController` (`ChangeNotifier`, `SharedPreferences`-backed) is wired into the dashboard's `Listenable.merge([...])` (`dashboard_screen.dart:228`) — confirmed a madhhab change triggers an immediate rebuild that re-invokes `CycleStatusEngine.evaluate(madhhab: MadhhabController.instance.selected, ...)` fresh, not from a cache. `fiqh-advisor-chat`'s client caller (`chat_view_model.dart`) also reads `MadhhabController.instance.selected` live at send time, not at widget-construction time.

Raw `cycle_entries` rows carry no madhhab field at all — confirmed the evaluator's `madhhab` parameter never touches persisted data, only computation — so the charter's "raw observations never change when madhhab changes" invariant holds structurally (there is nothing in the raw record that *could* change).

**Not verified this pass**: a live, all-12-directional-switch UI test (Hanafi→Maliki, Hanafi→Shafi'i, ... all 12 ordered pairs) confirming the Fiqh Report PDF, the dashboard, and (once built) any AI context all update in the same test run without residue. The reactive wiring described above makes this very likely to hold, but "very likely" is not the same as "tested" — recorded as an open item, not claimed as verified.

# AI User-State Context Layer Remediation Wave (2026-09-09)

Charter: the AICTX findings above, executed under an explicit "AICTX remediation only" scope — no fiqh rule/threshold/interpretation changes, no scholar review, no other domain's owner-gated items touched.

## Architecture built

**Before**: 4 independent Edge Functions, each deciding (or, in 3 of 4 cases, not deciding) what user-state to query, zero shared code, zero structured schema.

**After**: one canonical module, `supabase/functions/_shared/ai_user_context.ts`, exporting `buildUserAiContext()` (fetches pregnancy/cycle/wellbeing rows via the caller's own RLS-scoped `userClient` — never a service-role client, never a client-supplied `user_id`) and `formatContextBlock()` (renders a scoped `[CONTEXT]` text block per AI feature: `dr_niswah` / `general_assistant` / `fiqh_advisor` / `dream_interpreter`). All 4 Edge Functions now import and call these same two functions — one assembly path, not four.

**A real mistake made and caught during this wave, disclosed rather than hidden**: the first draft of this module reimplemented pregnancy-week/trimester math from scratch instead of reusing the already-existing, already-tested `pregnancy_status.ts` (previously living only inside `dr-niswah-chat/`) — exactly the "duplicated logic → drift risk" pattern `FIQH-5` already flagged, and the reimplementation used wrong `tracking_basis` string literals (a real bug). Caught before deployment by reading `pregnancy_status.ts` directly; fixed by moving it to `_shared/` (`git mv`, both the source and its existing, already-passing test file) and having the new module import and thinly adapt its real output instead. Verified via a real, executed test run (see Verification below) that this didn't regress the 16 pre-existing `pregnancy_status.test.ts` cases.

| Menstrual bleeding scan (`isCurrentlyBleeding`, `daysIntoCurrentEpisode`) | `cycle_entries` table | Persisted (raw); this scan is informational only | Derived (informational, explicitly labeled NOT a fiqh ruling) | Always fresh | Server, but explicitly non-authoritative for fiqh purposes |
| Selected madhhab | Client (`MadhhabController`, `SharedPreferences`) | Local only — no server table for this preference | Raw fact (user's own stated preference) | As fresh as the client's own state at call time | **Client** — genuinely exists only client-side; handled explicitly per Phase C, not queried server-side |
| Deterministic fiqh classification (`haid`/`tahara`/etc.) | Client (`MadhhabRuleEvaluator`/`CycleStatusEngine`, Dart) | Not persisted anywhere (confirmed `FIQH-3` — the DB column exists but is dead) | Derived, computed by the single canonical Dart engine | As fresh as the client's last computation | **Client** — genuinely exists only client-side today (see the "not reimplemented" note below); server treats it as `client_computed`, never independently verified |
| Wellbeing (mood/energy/sleep) | `wellbeing_logs` table | Persisted | Raw fact | Always fresh | Server |
| Wellbeing notes | **N/A — see `AICTX-13`, no such column exists in production** | — | — | — | — |
| Symptoms | `cycle_entries.symptoms` (JSONB, colon-encoded) | Persisted | Raw fact | Always fresh | Server |
| Cycle-entry notes | `cycle_entries.notes` | Persisted | Raw fact, explicitly labeled "user-authored statement, not verified fact" in every rendered context block | Always fresh | Server |
| Safety flags (current message) | Caller-supplied (e.g. `dr-niswah-chat`'s own real-time red-flag scan) | Not persisted | Raw, per-call | Current message only | Server, passed through, not derived by this module |

**The dead `fiqh_state` column (`FIQH-3`) was explicitly NOT used as a data source** — confirmed the module never selects it; the deterministic classification is sourced only from the client-supplied `clientFiqhState` field or omitted entirely, never from that stale, always-`'TAHARA'` column.

**Why the deterministic fiqh classification is not reimplemented server-side**: a real, deliberate design decision, not an oversight. `MadhhabRuleEvaluator`/`CycleStatusEngine` (Dart) is the one and only canonical implementation. Porting it to TypeScript would create a third parallel copy of fiqh math in this codebase (the first two being the now-removed dead `FiqhCalculationEngine` and the two already-flagged duplicate Dart copies, `FIQH-5`) — exactly the drift risk this whole audit exists to reduce. Per the charter's own Phase C instruction, client-only state is "handled explicitly," not hidden: the field is present, always labeled `classificationSource: 'client_computed'` (never asserted as independently server-verified), and every AI's system prompt is told explicitly it may reference but not treat this as its own conclusion. This limitation is tracked as `AICTX-10` below, not silently accepted.

## Phase E-K: architecture-level verification

- **Phase E (notes)**: only current-user notes are ever queried (RLS-enforced via `userClient`); edited/deleted notes disappear automatically since every call re-queries fresh, never caches; notes are explicitly labeled "user-authored statements, NOT verified facts" in every rendered context block; bounded to `notesLimit` (default 5) recent entries, not the full history; raw context text is never logged (only `console.error` calls elsewhere in these functions log structured metadata, never full context blocks — confirmed by reading every `console.error` call site, none include the context object).
- **Phase F (wellbeing)**: wired into `dr_niswah` and `general_assistant` scopes; explicitly distinguished as "user-entered wellbeing state," never elevated to a diagnosis anywhere in any prompt.
- **Phase G (freshness)**: architecturally guaranteed, not just tested for specific scenarios — `buildUserAiContext` has no caching layer of any kind; every call re-queries the database fresh. This structurally satisfies all 14 of the charter's named freshness scenarios (pregnancy change, period begin/end, corrections, madhhab change, mood add/edit, symptom add, note add/edit/delete, fiqh recompute, safety-flag change) without needing 14 separate invalidation mechanisms, because there is nothing to invalidate.
- **Phase H (cross-AI consistency)**: all 4 AI features now derive pregnancy/cycle/wellbeing/notes from the exact same `buildUserAiContext` call — by construction, they cannot disagree on these shared facts within the same moment, since it's the same function reading the same tables. Madhhab/fiqh classification remain client-supplied per-call, so consistency there depends on the client sending consistent values across calls in the same session (not independently verified this wave — see `AICTX-12`).
- **Phase I (deterministic authority)**: every system prompt (all 4, updated this wave) explicitly instructs the AI to explain, not override, deterministic/context state; none was given any mechanism to write back to the database — confirmed structurally, since none of the 4 functions' Gemini-response-handling code performs any DB write derived from the AI's own output (all DB writes remain exactly what they were before: chat message persistence, the `flagged_conversations` safety log).
- **Phase J (missing/conflicting context)**: `classificationSource: 'not_provided'` + an explicit `uncertainty` string is the designed behavior when the client doesn't supply a fiqh classification — every relevant prompt update explicitly tells the AI this means "do not assume a classification," matching the charter's "never guess" requirement.
- **Phase K (privacy/observability)**: re-verified — RLS/`userClient` isolation confirmed structurally (Phase C contract); no context payload is ever passed to `console.error`/`AppErrorReporter` anywhere in the touched files (confirmed by direct grep of every logging call site in all 4 functions and the shared module); deleted notes/wellbeing rows cannot reappear (no caching, fresh query every time).
