# Period tracking: implementation plan

Source of truth for each case is `PERIOD_TRACKING_COVERAGE.csv`, generated by
`scripts/period_tracking_register.py` from the verbatim case list in
`PERIOD_TRACKING_200_CASES.md`. This plan orders the work; it never replaces a
case's own row.

Product decision (2026-10-29): period tracking comes before qadha. Qadha is
only touched where existing behavior would otherwise become inconsistent or
unsafe (for example, predictions must never create qadha debt, PT-112).

## Invariants every change must keep

1. Observations, predictions, medical interpretation and fiqh classification
   stay separate. Fiqh state is computed on read, never stored.
2. A prediction is never written as an observation.
3. An unanswered day is "unrecorded", never "no bleeding".
4. No invented timestamps: date-only stays date-only.
5. An episode is never ended automatically.
6. Observations are never silently rewritten. A correction is a new row
   (`supersedes_id`) or an archived row plus a revision record.
7. No data moves between accounts. The owner is pinned when an operation is
   created.
8. "Saved" is shown only after the server confirms.
9. Predictions never produce qadha debt.

## Phase 1: baseline (done)

- All 200 cases are registered verbatim, each with an assessment, and the

- Code, migrations, tests, AGENTS.md and the open PRs were read.
